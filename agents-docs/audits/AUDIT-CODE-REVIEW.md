## Reconciliation summary

This is the deep-verify pass for the `code-review` domain, mirroring the reconciliation already done for dotnet/angular/sql/error-handling/logging/permissions/clean-slop. The tracker (`AUDIT-TRACKING.json`) already carried a blanket "resolved via PR #615" note on all 19 findings from an earlier bulk status update; this pass individually re-verified each finding against the current state of the referenced file(s) rather than trusting that blanket claim.

**Result: all 19 are genuinely fixed.** Every finding's specific fix was located in the current code (exact line/pattern cited in each tracker entry's `[2026-09-21 re-verified]` note) — no regressions, no partial fixes, no findings that need reopening. Highlights of what's now in place:

- `DashboardCacheEntry` carries a `plantingYear` field as part of its cache key; `_loadDashboardData` now guards on `_loadRequestId` like its siblings.
- The saved-list NLQ cache re-runs when `customers()` grows; `handleSelectLinkedCustomer` cancels prior in-flight fetches; the planting-intentions cache-hit path bumps `_piRequestId`.
- `_ensureDpForQuery` and `_appStateTicketsEffect` both now check the currently-selected trade unit before adopting a response/cache value, closing the two build-list cross-trade-unit races.
- The free-text unconfirmed-contract query now calls the canonical `isContractUnconfirmed()`; the free-text and refine-panel pacing calculations both use the full contract set now, resolving their prior contradiction.
- `BidSheetRepository.BulkUpsertBidsAsync` wraps new-location inserts in the same unique-violation catch/reconcile pattern as the rest of the class, backed by a real `ReconcileDuplicateLocationInsertsAsync` (previously the reconcile call only ever inspected bid entities).
- The three `DashboardRepository` upsert methods now group by (TradeUnitKey, PlantingYear) and build a fresh existing-row map per group, instead of assuming every item in a batch shares item 0's scope.
- `UsageTrackingMiddleware` records the activity record in a `finally` so requests that end in an unhandled exception are no longer invisible to usage analytics.
- `GeocodeService.SearchAsync` caches the full result list (not just the first result); `GeocodeBatchAsync` now acquires the shared rate-limiting semaphore per item.
- `ApiService._dedupe()` moved `finalize` upstream of `shareReplay`, so the in-flight cache entry is only evicted when the shared HTTP call itself completes, not on a single subscriber's teardown.
- Manage-Members search now cancels the prior in-flight request via a dedicated `Subject`; the scoped-notes fetch path now retries a superseded scope once the blocking fetch resolves instead of stranding it.
- `hasDeliveriesThisYear` reads `getUTCFullYear()` instead of a local-time getter, fixing the Jan 1 misclassification for US time zones.

No new findings were opened in this pass — the sampled areas (dashboard, build-list, home, customer-list races; bid-sheet/dashboard repository upsert logic; geocode service; NLQ filter service) showed no additional correctness issues beyond what was already tracked.

## Overall health

Correctness health for this domain is now good: every previously-identified race condition, stale-cache path, and logic mismatch in the sampled Angular components and .NET repositories/services has a confirmed, code-verified fix. The original observation still stands as useful context for future work — six of the original nineteen findings shared the same root-cause pattern (a fetch's response handler applying data without checking whether the selection/trade-unit/year context it was requested for was still current), recurring independently across home, dashboard, build-list, and customer-list. That the fixes landed as targeted per-site guards (request IDs, trade-unit-key comparisons, cache-key year fields) rather than a single shared utility is an acceptable outcome given each site had slightly different cancellation semantics, but a shared "stale-response guard" helper would still be worth extracting if a similar race turns up in new code.

## 2026-10-13 calibration pass

Scope for this run: a `code-review`-only pass from the Code Quality Dashboard calibration queue (`audit/pilot-20261013`), one domain per invocation, continuing on the same branch already checked out.

**Fresh sample of new churn.** 116 commits touched `api/`/`client/` since the 2026-09-28 pass, dominated by a new Bin Sites & Grain on Farm feature area, a `fix_BuildListTradeUnitReloadGate` branch (four self-correcting commits landed same-day, each fixing a regression the previous one introduced), a usage-dashboard authorization simplification (`feature_UsageDashboardManagerForAll`), and a CTRM contract-read strategy default flip. Targeted the highest-risk areas rather than the full diff:

- `build-list.component.ts` — the trade-unit reload gate (`_loadFresh`, `processQuery`, `_parkedQuery`, `_cancelLoad$`, `clearQuery`). This is exactly the stale-response-race pattern this domain has repeatedly found bugs in (6 of the original 19 findings shared this root cause). Traced the parked-query re-entry logic end to end: a prompt picked while `coreDataLoaded()` is false is parked with an explicit marker (not inferred from `isProcessing && !hasGenerated`, which the authors found and fixed was ambiguous with a saved-list's own in-flight fetch); a second trade-unit change or `clearQuery()` correctly drops the parked marker; a reload in flight is cancelled via `_cancelLoad$` when the selection goes empty. `build-list.trade-unit-reload.spec.ts` (277 lines, 8 cases) directly covers every race condition this code's comments describe, including the exact "parked prompt dropped by a second TU change" and "saved-list fetch not discarded by a background refresh" scenarios a less careful reader would miss. No gap found — this is the domain's own prior findings being used as a checklist by the team, and it holds up.
- `PlantingIntentionService.ResolveTradeUnitAsync` (api/GrainOriginatorPortal.Api/Services/PlantingIntentionService.cs) — flagged as the top follow-up target in the 2026-09-28 report and unread until now. Found materially reworked since then (`feat(planting): ask where the acres go when a trade unit is removed`, `fix(planting): record planting intentions against the chosen trade unit`): the caller's trade-unit choice is now validated against the producer's active memberships (400 if it isn't one of them), falls back to a deterministic first-by-code membership when the caller sends nothing, and accepts the caller's choice unvalidated only when the producer has zero membership rows (contracts-only producers). `GetActiveTradeUnitCodesAsync` orders by `TradeUnit` so the "first membership" fallback is genuinely deterministic, not call-order-dependent. Backed by `PlantingIntentionServiceTests.cs`. No gap found.
- `UsageDashboardAccess.cs` / `UsageDashboardController.cs` (api/GrainOriginatorPortal.Api/Authorization, Controllers) — the `UsageDashboardViewAllUsers` allowlist table and its synthetic role were dropped in favor of "every Admin sees every manager's team"; exclusion management stays double-gated (AdminOnly policy + a separate `ExclusionManagers` config allowlist, checked again in each handler body). This is a genuine authorization-shape change, but it's accompanied by a new `SECURITY-REVIEWS/ACCEPTED-RISKS.md` entry and an EF migration dropping the now-unused table, and reads as a deliberate, already-reviewed design simplification rather than an overlooked gap. No correctness issue found; flagging only because it's exactly the kind of change this domain's severity table calls out ("missing authorization in a non-security-focused review") — worth a second look from whoever owns the dedicated security/permissions audit passes, not reopening here.

**Result: no new findings opened.** The highest-risk new code (the trade-unit reload gate, which is this codebase's recurring bug pattern; the previously-flagged planting-intention trade-unit resolution; the usage-dashboard auth simplification) all held up under direct reading. Not sampled this pass, for a future invocation with more budget: the Bin Sites & Grain on Farm feature's larger surface (`grain-on-farm.ts`'s dual-read migration logic was spot-checked on 2026-09-28 but the newer commits — bin-site filters, sold-bushels/last-bid aggregation, the `merge-producer-rows.ts` consumers — were not), and the CTRM trade-unit-contract-read default flip (`Ctrm:TradeUnitContractStrategy` now defaults to `tradeUnit`) — the underlying `CtrmContractReader`/throttle logic was reviewed and found correct on 2026-09-28, so this is a config-default change against already-reviewed code, but the behavioral change itself (producer click is a live per-producer read again) was not independently verified against a real CTRM response this pass.
