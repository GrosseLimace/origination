## What is Git?

**Git** is a version control system — think of it as "Track Changes" for your entire project, shared across your whole team.

Without Git, collaborating on code means emailing files back and forth, overwriting each other's work, and losing track of what changed and when. Git solves all of these problems:

- **It tracks every change**: Every edit anyone makes is recorded. You can see who changed what, when, and why.
- **It enables teamwork**: Multiple developers can work on the same project — even the same files — at the same time, without stepping on each other's toes.
- **It provides a safety net**: If something breaks, you can always go back to a previous version that worked.
- **It keeps a complete history**: The full timeline of your project is preserved, from the first line of code to the latest update.

Git is the industry standard. It's used by virtually every software team in the world, from two-person startups to organizations with thousands of developers.

## Key Vocabulary

These are the essential terms you'll encounter when working with Git. Each one is defined in plain language and will be reinforced throughout this guide.

| Term | What It Means |
|------|---------------|
| **Repository (repo)** | Your project folder, plus the complete history of every change ever made. Think of it as a project that remembers everything. |
| **Clone** | Making a copy of a repository from GitHub onto your computer. This is how you get started on an existing project. |
| **Branch** | A separate workspace where you can make changes without affecting anyone else. Like making a copy of a document to edit — the original stays untouched until you're ready. |
| **Main** | The primary branch. This is the "official" version of the project. All finished work eventually ends up here. |
| **Commit** | A snapshot of your changes at a specific moment. Like clicking "Save" — but Git remembers every save you've ever made. |
| **Stage** | Selecting which changes you want to include in your next commit. You choose what to save before you save it. |
| **Push** | Sending your commits from your computer up to GitHub so your teammates can see them. |
| **Pull** | Downloading the latest changes from GitHub onto your computer so you have everyone's most recent work. |
| **Remote** | The version of your repository that lives on GitHub (as opposed to your computer). |
| **Local** | The version of your repository on your computer (as opposed to GitHub). |
| **Merge** | Combining changes from one branch into another. This is how your work gets incorporated into the main project. |
| **Pull Request (PR)** | A request to merge your branch into `main`. It lets your teammates review your changes before they become part of the official project. |
| **Conflict** | When two people change the same lines in the same file, Git can't automatically combine them. You'll need to decide which changes to keep. |

## How Git Works (The Mental Model)

### Three Places Your Code Lives

When you work with Git, your code exists in three places:

```
┌─────────────────┐         push →         ┌─────────────────┐
│   Your Computer │ ───────────────────── │     GitHub       │
│     (local)     │ ←───────────────────── │    (remote)      │
└─────────────────┘         ← pull         └─────────────────┘
         │
         │  Your working files
         │  + Git's history of every change
```

1. **Your computer (local)** — where you write and edit code. Git tracks all your changes here.
2. **GitHub (remote)** — the shared home for your project. This is where your team collaborates.
3. **Your branch vs. main** — your personal workspace vs. the official project.

When you **push**, you send your **commits** from your **local** machine to the **remote** on GitHub. When you **pull**, you download the latest **commits** from the **remote** to your **local** machine.

### What is a Branch?

Think of `main` as a highway — it's the well-traveled road where the finished, tested code lives.

A **branch** is like an exit ramp. You leave the highway, do your work in a safe space, and when you're done, you merge back onto the highway. Meanwhile, other developers are on their own exit ramps, working on their own features, and none of you are getting in each other's way.

```
main:       ●───●───●───●───●───●───●───●
                     \             /
feature/login:        ●───●───●──┘
                          (your work)
```

This is the power of Git: **everyone works simultaneously**, and Git brings it all together.

## Your Development Environment

### VS Code Source Control

VS Code has Git built in. Open the **Source Control** panel with `Ctrl+Shift+G` (or click the branch icon in the left sidebar).

**What the icons mean:**

| Icon | Meaning |
|------|---------|
| **M** | Modified — you changed an existing file |
| **U** | Untracked — this is a new file Git hasn't seen before |
| **A** | Added — a new file that's been staged for commit |
| **D** | Deleted — a file that's been removed |

The **status bar** at the bottom of VS Code shows your current **branch** name and sync status (how many commits to push/pull).

### Recommended Extensions

Install these two extensions to get the most out of Git in VS Code:

| Extension | What It Does |
| --- | --- |
| **[GitHub Repositories](https://marketplace.visualstudio.com/items?itemName=GitHub.remotehub)** | Browse, search, and edit any GitHub repository directly in VS Code — without cloning it to your machine. Great for quick edits and exploring other projects. |
| **[GitHub Pull Requests](https://marketplace.visualstudio.com/items?itemName=GitHub.vscode-pull-request-github)** | Review pull requests, leave comments, and manage issues without leaving VS Code. This is how you'll review your teammates' code. |

To install: open the **Extensions** panel (click the square icon in the left sidebar or press `Ctrl+Shift+X`), search for the extension name, make sure the publisher name is 'GitHub' and that it has the blue checkmark [trusted extension] and click **Install**.

### Claude Code as Your Git Assistant

Claude Code can handle Git operations for you through natural language. Here are example prompts you can use:

| What You Want to Do | What to Tell Claude Code |
|---------------------|--------------------------|
| Get latest changes | *"Pull the latest changes from main"* |
| Create a branch | *"Create a new feature branch called feature/add-login-page"* |
| Commit your work | *"Commit my changes with the message: feat(auth): add login form"* |
| Push to GitHub | *"Push my branch to GitHub"* |
| Create a PR | *"Create a pull request for my branch"* |

### When to Use What

- **VS Code Source Control panel** — great for visually reviewing changes, staging specific files, and seeing the diff (what changed in each file)
- **Claude Code** — great for multi-step operations, creating branches, writing commit messages, resolving conflicts, and when you're not sure what command to run

Both approaches accomplish the same thing. Use whichever feels more comfortable, or mix and match.

## The Basic Workflow

This is the standard process every developer follows. It has six steps:

```
 ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
 │ 1. Clone │──→│  2. Pull │──→│ 3. Branch│──→│ 4. Commit│──→│ 5. Push  │──→│  6. PR   │
 │  (once)  │   │from main │   │ (create) │   │  (save)  │   │ (publish)│   │ (review) │
 └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘   └──────────┘
```

### Step 1: Clone the Repository (One-Time Setup)

Before you can work on a project, you need to **clone** it — that means downloading a full copy of the repository from GitHub onto your computer. You only need to do this once per project.

**Where should I clone to?** Create a dedicated folder for your projects under your user directory:

```
C:\Users\<your-name>\<create-folder-here>
```

> Replace `<your-name>` with your Windows username and `<create-folder-here>` with a folder name of your choice (e.g., `Projects`, `Repos`, `Dev`). If the folder doesn't exist yet, create it first.

**In VS Code:**

1. Open VS Code and click **Clone Repository** on the Welcome tab (or click **Clone Repository** in the Source Control panel if no folder is open)
2. Paste the repository URL from GitHub (click the green **Code** button on the repo page → copy the HTTPS URL)
3. When prompted to choose a folder, navigate to `C:\Users\<your-name>\<create-folder-here>`
4. VS Code will create a subfolder with the repository name and open it for you

**With Claude Code:**
> *"Clone the repository https://scoular.ghe.com/your-org/project-name into my Projects folder"*

**On GitHub Enterprise — finding the clone URL:**

1. Go to the repository on `scoular.ghe.com`
2. Click the green **Code** button
3. Copy the **HTTPS** URL (it looks like `https://scoular.ghe.com/your-org/repo-name.git`,
   where `your-org` is whichever org owns the repo)

Scoular code lives on Scoular-hosted remotes only — any org or personal
namespace on `scoular.ghe.com`, or `dev.azure.com/sco-iaa/IAA/*`. Never push
a work repository to a personal github.com account.

After cloning, you have a complete copy of the project — all files, all branches, and the full history. You're ready to start working.

### Step 2: Pull from Main

Before you start any new work, make sure you have the latest version of the project.

**Why?** Other teammates may have merged their work since you last looked. **Pulling** ensures your starting point includes everyone's latest changes.

**In VS Code:**

1. Switch to the `main` **branch** (click the branch name in the bottom-left status bar → select `main`)
2. Click the sync icon (circular arrows) in the status bar, or open the Source Control panel and click **Pull**

**With Claude Code:**
> *"Switch to main and pull the latest changes"*

### Step 3: Create a Feature Branch

Never work directly on `main`. Instead, create a **branch** — your own workspace.

**Why?** If you work on `main` directly, your half-finished changes mix with everyone else's finished work. A **branch** keeps your work isolated until it's ready.

**In VS Code:**

1. Click the **branch name** in the bottom-left status bar (it probably says `main`)
2. Select **"Create new branch..."** from the dropdown
3. Name your branch following the convention: `feature/short-description`
   - Example: `feature/add-export-button`, `feature/123-fix-login`

**With Claude Code:**
> *"Create a new branch called feature/add-export-button"*

> For the full naming rules, see [Branch Naming Conventions](git-reference.md#branch-naming-conventions) in the Git Reference.

### Step 4: Make Changes and Commit

Now do your work — write code, edit files, add features. When you reach a good stopping point, save a snapshot by creating a **commit**.

**What makes a good commit?** Think of commits as save points in a video game. Save often, and save at meaningful moments:

- Finished a small piece of functionality
- Got something working that wasn't working before
- About to try something risky (save first!)

**In VS Code:**

1. Open the Source Control panel (`Ctrl+Shift+G`)
2. Review your changes — click any file to see the diff (what changed)
3. **Stage** the files you want to commit by clicking the `+` icon next to each file (or click `+` next to "Changes" to stage everything)
4. Type a **commit** message in the text box at the top
5. Click the checkmark button (or press `Ctrl+Enter`) to **commit**

**With Claude Code:**
> *"Commit my changes with the message: feat(auth): add login form validation"*

**Writing commit messages:** Keep them short and descriptive. Our team uses this format:

```
type(scope): description
```

Examples: `feat(auth): add login form`, `fix(api): resolve timeout error`, `docs(readme): update setup instructions`

> For the complete commit message guide, see [Commit Message Standards](git-reference.md#commit-message-standards) in the Git Reference.

**Commit often.** Small, frequent **commits** are much easier to review and undo than one massive commit at the end.

### Step 5: Push Your Changes

Once you've committed your work locally, you need to **push** it to GitHub so your teammates can see it. **Pushing** sends your **local commits** to the **remote** on GitHub.

The first time you push a new branch, you're **publishing** it — creating the branch on GitHub. After that, each push sends your latest commits.

**In VS Code:**

1. Click **Publish Branch** in the Source Control panel (first time pushing a new branch)
2. For subsequent pushes, click the sync icon (circular arrows) in the status bar

**With Claude Code:**
> *"Push my branch to GitHub"*

**Push regularly** — don't wait until the feature is 100% done. Pushing often means your work is backed up on GitHub, and teammates can see your progress.

### Step 6: Create a Pull Request

When your feature is ready for review, open a **Pull Request (PR)**.

A **Pull Request** is how you ask your team to review and approve your changes before they go into `main`.

**In VS Code:**

1. After pushing, VS Code may show a notification to create a PR — click it
2. Or install the "GitHub Pull Requests" extension for a full PR workflow inside VS Code

**With Claude Code:**
> *"Create a pull request for my branch"*

**On GitHub (web):**

1. Go to your repository on GitHub
2. You'll see a banner: "Your branch had recent pushes" — click **Compare & pull request**
3. Fill in:
   - **Title**: Short summary (e.g., `feat(auth): add login form`)
   - **Description**: What you changed and why, any testing notes
   - **Reviewers**: Add your teammates
4. Click **Create pull request**

**What happens next:**

- Your teammates review the code
- They may leave comments or request changes
- Address any feedback and push additional commits to the same branch
- Once approved, the PR gets **merged** into `main`

### After Your PR is Merged

Once your code is in `main`, clean up:

**In VS Code:**

1. Switch back to `main` (click branch name in status bar → select `main`)
2. **Pull** the latest changes (your merged code is now in `main`!)
3. Delete your feature **branch** — it's no longer needed

**With Claude Code:**
> *"Switch to main, pull the latest, and delete my feature branch"*

## Dealing with Merge Conflicts

### What is a Merge Conflict?

A **conflict** happens when two people change the **same lines** in the **same file**. Git handles most changes automatically — if you edit file A and your teammate edits file B, no problem. Even if you both edit the same file but different sections, Git merges them seamlessly.

But when you both change the exact same lines, Git doesn't know which version to keep. It pauses and asks you to decide. **This is completely normal** — it's not an error, and it's not something you did wrong.

### How to Recognize a Conflict

When a **conflict** occurs, the affected files will be marked in VS Code's Source Control panel with a **C** (conflict) icon. If you open the file, you'll see markers like this:

```
<<<<<<< HEAD (your changes)
function validateEmail(email) {
    return email.includes('@') && email.includes('.');
}
=======
function validateEmail(email) {
    return /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email);
}
>>>>>>> main (incoming changes)
```

- Everything between `<<<<<<< HEAD` and `=======` is **your version**
- Everything between `=======` and `>>>>>>>` is the **other version** (from `main` or another branch)

### Resolving Conflicts in VS Code

VS Code has a built-in merge editor that makes this much easier than editing the markers by hand:

1. **Open the conflicted file** — VS Code highlights the conflicting sections
2. **Use the inline buttons** that appear above each conflict:
   - **Accept Current Change** — keep your version
   - **Accept Incoming Change** — keep the other version
   - **Accept Both Changes** — keep both (you'll clean up the result)
   - **Compare Changes** — see them side by side
3. **Review the result** — make sure the combined code makes sense
4. **Stage the resolved file** — click the `+` icon in the Source Control panel
5. **Commit** — this saves the resolution

**With Claude Code:**
> *"Help me resolve the merge conflict in src/auth/login.ts"*

Claude Code can analyze the conflicting changes, explain what each version does, and help you decide which to keep — or combine them intelligently.

### Preventing Conflicts

Conflicts are inevitable when teams collaborate, but you can minimize them:

- **Pull from main frequently** — the more up-to-date your **branch** is, the fewer conflicts you'll encounter
- **Keep branches short-lived** — finish features quickly and merge them. Long-running branches accumulate more differences from `main`
- **Communicate with your team** — if you know a teammate is working on the same file, coordinate to avoid editing the same sections
- **Commit small, commit often** — small changes are easier to merge than large, sweeping changes

## Common Situations and Solutions

### "I committed to the wrong branch"

You made changes on `main` (or the wrong feature branch) by mistake.

**With Claude Code:**
> *"I accidentally committed to main. Move my last commit to a new branch called feature/my-feature"*

**What Claude Code will do:**

1. Create a new branch with your commit
2. Reset `main` back to where it was before your mistake
3. Switch you to the new branch

### "I need to undo my last commit"

You committed something you didn't mean to. No problem.

**With Claude Code:**
> *"Undo my last commit but keep the changes in my working files"*

This removes the **commit** but leaves your edits in place, so you can modify them and commit again.

> *"Undo my last commit and discard the changes completely"*

This removes both the **commit** and the edits. Use this when you want to start over.

**In VS Code:**

1. Open the **Source Control** panel (`Ctrl+Shift+G`)
2. Click the **`···`** (more actions) menu at the top of the panel
3. Select **Commit** → **Undo Last Commit**
4. Your changes return to the **staging** area

### "My branch is behind main"

Your teammates merged new code into `main` while you were working. Your **branch** is now outdated.

**With Claude Code:**
> *"Update my branch with the latest from main"*

**In VS Code:**

1. Make sure your current changes are **committed** (don't try this with uncommitted work)
2. Open the **Source Control** panel (`Ctrl+Shift+G`)
3. Click the **`···`** (more actions) menu → select **Branch** → **Merge Branch...** → choose `main`
4. If there are **conflicts**, resolve them (see [Dealing with Merge Conflicts](#dealing-with-merge-conflicts))

**Do this regularly** — updating from `main` often means smaller, easier merges.

### "I accidentally committed a file I shouldn't have"

You committed a file that shouldn't be in the repository (a large file, a personal config file, a file with secrets).

**With Claude Code:**
> *"Remove the file config/secrets.json from Git tracking but keep it on my local machine"*

**Preventing this in the future:** Your project should have a `.gitignore` file that tells Git which files to ignore (build output, personal settings, secrets). If a file type keeps getting committed by accident, add it to `.gitignore`.

> *"Add *.env files to .gitignore"*
