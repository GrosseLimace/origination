## Branching Strategy Overview

We use a **Modified GitHub Flow** — a lightweight branching model where `main` is always production-ready and all work happens in short-lived feature branches.

### Default Workflow: Feature Branch → Main

For most work, this is the only pattern you need:

```
┌──────────────────────────────────────────────────────────┐
│                      main (production-ready)              │
│  ════════════════════════════════════════════════════     │
│         ↑              ↑              ↑                   │
│    [feature/a]    [feature/b]    [hotfix/x]              │
└──────────────────────────────────────────────────────────┘
```

1. Create a feature branch from `main`
2. Do your work, commit regularly
3. Open a pull request to `main`
4. After review and approval, merge to `main`

This is the simplest workflow and should be your default approach. See [Git 101 — The Basic Workflow](git-101.md#the-basic-workflow) for the step-by-step walkthrough.

### Branch Types

| Branch Type | Created From | Merges To | Deploy | Lifetime |
|-------------|--------------|-----------|--------|----------|
| `main` | — | — | Production (planned releases) | Permanent |
| `feature/*` | `main` | `main` | — | Until feature complete |
| `integration/*` | `main` | `main` (or features merged separately) | Test/Staging | Until testing complete |
| `hotfix/*` | Most recent release tag | `main` (after deploy) | Production (directly) | Until fix deployed |

### Choosing Your Workflow

| Scenario | Approach |
|----------|----------|
| Single feature, independent of others | Feature branch → PR → main |
| Multiple features, can be deployed independently | Each feature branch → PR → main (separately) |
| Multiple features that must be tested together | Create integration branch, test, then merge |
| Urgent production fix | Branch from latest tag → deploy hotfix → tag → merge to main |
| Planned production deployment | Merge to main, deploy main, tag with version |

## Integration Branches

Sometimes multiple feature branches need to be tested together before any of them merge to main. Use a temporary **integration branch** for this.

### When to Use Integration Branches

- Two or more features interact and need combined testing
- You want to verify features work together before going to production
- QA needs a single deployment that includes multiple in-progress features

### Creating an Integration Branch

```
┌──────────────────────────────────────────────────────────┐
│                      main (production-ready)              │
│  ════════════════════════════════════════════════════     │
│         ↑                   ↑                             │
│    [feature/a]         [feature/b]                       │
│         ↑                   ↑                             │
│         └─────────┬─────────┘                             │
│                   │                                       │
│           [integration/xyz]  ← temporary, testing only    │
└──────────────────────────────────────────────────────────┘
```

**In VS Code / Claude Code:**

1. Switch to `main` and pull the latest changes
2. Create a new branch named `integration/<description>` (e.g., `integration/sprint-5-testing`)
3. Merge each feature branch into the integration branch
4. Resolve any conflicts (only once, here)
5. Push the integration branch for deployment to the test environment

> For the CLI commands, see [Integration Branch Commands](git-reference.md#branch-management--integration-branches) in the Git Reference.

### After Integration Testing Passes

Choose one of two approaches based on your situation:

**Option A: Merge integration branch directly to main** (recommended when features are coupled)

- Create a PR from the integration branch to `main`
- After merge, delete the integration branch and the feature branches
- Use this when: features are tightly coupled, conflicts were resolved in the integration branch, or you want to deploy exactly what was tested

**Option B: Merge each feature separately to main**

- Create a separate PR for each feature branch
- Delete the integration branch after all features are merged
- Use this when: features could ship independently, you want granular PR history, or you may need to drop one feature

| Situation | Recommended |
|-----------|-------------|
| Features are tightly coupled, must deploy together | **Option A** |
| Conflicts were resolved in integration branch | **Option A** |
| Want to deploy exactly what was tested | **Option A** |
| Features could ship independently | **Option B** |
| Need granular PR history per feature | **Option B** |
| May need to drop one feature | **Option B** |

## Hotfix Workflow

A **hotfix** is an urgent fix for a production issue that can't wait for the normal development cycle.

### Why Hotfixes Are Different

If `main` has moved forward since your last production deployment (new features merged), you can't simply deploy `main` — it would include unreleased code. By branching from the most recent release **tag** and deploying the hotfix branch directly:

- You deploy exactly what's in production + your fix
- No unreleased features slip into production
- `main` can continue receiving feature merges without affecting hotfixes

### Hotfix Process

```
v1.2.0 (in production)
   ↓
hotfix/v1.2.1-fix-login ──→ deploy to production ──→ tag v1.2.1
                         ↘ merge to main (keep main current)
```

1. **Branch from the most recent release tag** (not from `main`)
2. Make your fix and commit
3. Push the hotfix branch
4. **Deploy the hotfix branch directly to production**
5. Tag the hotfix as the new production release
6. Merge the hotfix to `main` via PR (so `main` has the fix too)
7. Delete the hotfix branch

> **VS Code Note**: VS Code cannot create a branch from a tag directly in the UI. Use Claude Code ("Create a branch called hotfix/v1.2.1-fix-login from tag v1.2.0") or see [Hotfix CLI Commands](git-reference.md#branch-management--hotfix-branches) in the Git Reference.

### Subsequent Hotfixes

Each hotfix tag becomes the new baseline. If you need another hotfix, branch from the **most recent tag**:

```
v1.2.0 → hotfix → v1.2.1 → hotfix → v1.2.2 → hotfix → v1.2.3
                                                         ↓
                                              (current production)
```

### Emergency Procedures

For **P0 incidents** (production is down, critical security issue):

1. Follow the standard hotfix workflow above, but with expedited review
2. A single code owner approval is sufficient for emergency PRs
3. If the standard process is too slow, deploy the fix directly and document in Teams
4. **Always open a retroactive PR** to merge the emergency fix to `main`
5. Conduct a brief post-incident review to capture what happened

> Emergency bypasses should be rare. Track them as part of your [release management metrics](#metrics-and-review).

## Releases and Tagging

Use **tags** to mark production releases. Tags provide an immutable reference to exactly what was deployed, allowing you to create hotfix branches from any past release.

### Semantic Versioning

Every production deployment should be tagged using semantic versioning:

```
v{Major}.{Minor}.{Patch}
```

| Component | When to Increment | Example |
|-----------|------------------|---------|
| **Major** | Breaking changes | `v1.0.0` → `v2.0.0` |
| **Minor** | New features (backward-compatible) | `v1.0.0` → `v1.1.0` |
| **Patch** | Bug fixes | `v1.1.0` → `v1.1.1` |

### Creating a Release

**Using Claude Code:**

> "Tag the current main branch as v1.2.0 with the message 'Release 1.2.0: user authentication and profile features'"

**Using GitHub CLI:**

```bash
gh release create v1.2.0 --title "Release 1.2.0" --notes "## What's New
- User authentication
- User profile management
- Bug fixes"
```

> For the full set of tagging CLI commands, see [Tagging and Releases](git-reference.md#tagging-and-releases) in the Git Reference.

### Tags vs Release Branches

| Approach | Pros | Cons |
|----------|------|------|
| **Tags** (recommended) | Immutable, lightweight, no maintenance | Need CLI for hotfix branching |
| **Release branches** | Visual in UI, familiar | Accumulate over time, can become stale |

Tags give you the same capability as release branches (a reference point for hotfixes) without the maintenance overhead. You can always create a branch from a tag when needed.

## Release Management

This section captures our release management approach for GitHub Enterprise repositories in the IT organization.

> **Status**: Phase 1 Pilot — 12-week trial period, reassessment in April 2026.

### Scope

- Applies to IT repositories in `https://scoular.ghe.com/IT`
- Covers branch strategy, approvals, environments, and deployment practices

### Environment Model

**Default (3 environments):**

| Environment | Deploy From | Trigger | Approval |
|-------------|-------------|---------|----------|
| `dev` | `main` | Auto-deploy | None |
| `qa` | `main` or `integration/*` | Manual | Required |
| `prod` | `main` | Manual | Required |

**Alternative (4 environments)** — use when UAT should be isolated from internal QA cycles:

| Environment | Deploy From | Trigger | Approval |
|-------------|-------------|---------|----------|
| `dev` | `main` | Auto-deploy | None |
| `qa` | `main` or `integration/*` | Manual | Required |
| `uat` | `main` | Manual | Required |
| `prod` | `main` | Manual | Required |

Deployments default to **Azure App Service slot-based deployments**.

### Branch and PR Rules

- All work in `feature/*`, `bugfix/*`, `hotfix/*` branches
- PR required to merge to `main`
- **1 code owner approval** required (Phase 1)
- Passing CI checks required (build + tests)
- Linear history enforced; no merge commits

> **Note on linear history**: Enforcing linear history means all PRs must be rebased onto `main` before merging (no merge commits). This keeps the commit history clean and easy to follow. Your merge strategy should be set to "Rebase and merge" or "Squash and merge" in GitHub settings.

### Access Model

| Role | Permissions |
|------|-------------|
| **IT org members** | Read repos, create branches, submit PRs |
| **Maintainers** | Approve PRs to `main` |
| **Deployers** | Approve QA/UAT/Prod deployments |
| **Admins** | Manage repo settings |

### Branch Protection (Main)

- Require PR before merge
- Require code owner review
- Require passing checks
- Restrict direct pushes to maintainers
- Block force pushes

> For the full protection rules table and setup instructions, see [Branch Protection Rules](git-reference.md#branch-protection-rules) in the Git Reference.

### Metrics and Review

Track these metrics during the pilot:

| Metric | What It Tells You |
|--------|-------------------|
| PR volume and lead time | How fast work flows from branch to main |
| Deployment frequency | How often code reaches production |
| Rollback count | How stable deployments are |
| Emergency bypasses | How often the process is circumvented |

**Review outcomes at Week 13 (April 2026)** and decide on next maturity steps.

### Open Decision Points

These items need team input and will be resolved during the pilot:

- **Squash vs merge commits** — Squash keeps history clean; merge preserves granular commit history
- **1 vs 2 approvals** for high-risk applications
- **Whether QA/UAT can deploy from `integration/*`** branches
- **If and when to adopt release branches or feature flags**

## Pull Request Best Practices

### Before Creating a PR

- [ ] All tests pass locally
- [ ] Code follows style guidelines
- [ ] Commits are clean and well-messaged (see [Commit Message Standards](git-reference.md#commit-message-standards))
- [ ] Branch is rebased on latest `main`
- [ ] Documentation is updated (if applicable)
- [ ] Related issue is linked

### PR Title Format

Use the same format as commit messages:

```
feat(auth): implement two-factor authentication
fix(export): resolve CSV encoding issue
docs(api): update endpoint documentation
```

### PR Description Template

Create `.github/PULL_REQUEST_TEMPLATE.md` in your repository:

```markdown
## Summary
Brief description of what this PR accomplishes.

## Changes
- Change 1
- Change 2
- Change 3

## Testing
- [ ] Unit tests added/updated
- [ ] Integration tests pass
- [ ] Manual testing completed

## Related Issues
Fixes #(issue number)

## Screenshots (if applicable)
[Add screenshots here]

## Checklist
- [ ] My code follows the project's style guidelines
- [ ] I have performed a self-review
- [ ] I have commented my code where necessary
- [ ] I have updated the documentation
- [ ] My changes generate no new warnings
```

### Reviewing PRs

**As a reviewer:**

1. Review within 24 hours when possible
2. Provide constructive, specific feedback
3. Use GitHub's suggestion feature for simple changes
4. Distinguish between required changes and suggestions (use "nit:" prefix)
5. Approve only when satisfied with quality

**Prefer inline comments over general conversation.** When you have feedback about a specific piece of code, leave it as an **inline comment** directly on that line in the "Files changed" tab — not as a general comment in the PR's "Conversation" tab. This makes your feedback:

- **Precise** — the author sees exactly which line you're referring to
- **Actionable** — no guessing about "which function did they mean?"
- **Easier to track** — inline comment threads can be individually resolved

Reserve general PR conversation comments for high-level observations that don't map to a specific line (e.g., architectural concerns, questions about scope, or overall praise).

**How to leave inline comments:**

1. Open the PR and go to the **Files changed** tab
2. Hover over a line number — a blue **+** icon appears
3. Click **+** to comment on a single line, or click and drag to select a range of lines
4. Write your comment. Use the **suggestion** feature (click the `+-` icon in the toolbar) to propose exact code changes the author can accept with one click
5. Click **Add single comment** for standalone feedback, or **Start a review** to batch multiple comments and submit them together

> **Tip**: Always batch your comments into a single review rather than posting them one at a time. Individual comments each send a notification — batching is less noisy and gives the author a complete picture at once.

**GitHub Review Actions:**

- **Comment**: General feedback, no approval decision
- **Approve**: Code is ready to merge
- **Request changes**: Required changes before merging

**Addressing feedback:**

1. Respond to all comments
2. Push fixes as new commits (easier to review)
3. Re-request review after changes
4. Use "Resolve conversation" when addressed

### Using GitHub Features

**Draft Pull Requests:**

- Create as draft when work is in progress
- Convert to ready when ready for review
- Use for early feedback without formal review

**Auto-merge:**

- Enable auto-merge when PR is approved
- Automatically merges when all requirements are met

**Merge Options:**

- **Squash and merge**: Combines all commits into one (recommended for most feature branches)
- **Rebase and merge**: Applies commits on top of base branch (linear history)
- **Create a merge commit**: Preserves all commits and creates merge commit

> **Note**: If linear history is enforced on your repository, only "Squash and merge" and "Rebase and merge" are available.

## Advanced Best Practices

### Do's

- **Commit often**: Small, focused commits are easier to review and revert
- **Pull before push**: Always pull latest changes before pushing
- **Review before committing**: Use `git diff` to verify changes
- **Write meaningful messages**: Future you will thank present you (see [Commit Message Standards](git-reference.md#commit-message-standards))
- **Delete merged branches**: Keep the repository clean
- **Tag releases**: Use semantic versioning (v1.2.3)
- **Use GitHub CLI**: Streamlines common operations

### Don'ts

- **Don't commit to `main` directly**: Always use pull requests
- **Don't force push shared branches**: Only force push personal branches
- **Don't commit secrets**: Use environment variables or GitHub Secrets
- **Don't commit large binary files**: Use Git LFS if necessary
- **Don't ignore merge conflicts**: Resolve them carefully (see [Dealing with Merge Conflicts](git-101.md#dealing-with-merge-conflicts))
- **Don't amend pushed commits**: Creates problems for collaborators

### Keeping Branches Updated

When your branch falls behind `main`, you need to bring in the latest changes:

**In VS Code / Claude Code:**

> "Update my branch with the latest from main"

This will either merge `main` into your branch or rebase your branch on top of `main`, depending on your repository's settings.

> For the CLI commands (merge vs rebase), see [Daily Workflow Commands](git-reference.md#daily-workflow-commands) in the Git Reference.

**Important**: Don't rebase branches that others are working on. Rebase rewrites history, which can cause problems for collaborators.

### Recovering from Mistakes (Advanced)

| Situation | Solution |
|-----------|----------|
| Undo last commit (keep changes) | `git reset --soft HEAD~1` |
| Undo last commit (discard changes) | `git reset --hard HEAD~1` |
| Revert a pushed commit (safe) | `git revert <commit-hash>` |
| Restore a deleted branch | `git checkout -b <name> <commit-hash>` |
| Find lost commits | `git reflog` |

> For basic recovery scenarios (wrong branch, undo, behind main), see [Common Situations](git-101.md#common-situations-and-solutions) in Git 101.
